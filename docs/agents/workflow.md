# 需求到交付

用户用自然语言描述需求即可。Agent 负责选择流程、读取材料和执行工具，不要求用户记住 slash command。本文是本仓库的执行约定；本机、云端及不同厂商的 Agent 使用同一流程。

## 开始

1. 读根目录 `AGENTS.md`，检查工作区，再读对应 issue 的完整正文和评论。
2. 涉及开发、领取任务或交接时，按 `collaboration.md` 查询 GitHub 当前状态。聊天记录与本地文件不能替代已经推送的规格和代码。
3. 按下面的分支选择工作量；向用户简短说明选择后直接执行已授权的工作。

| 情况 | 执行流程 | 可用且允许自动调用时使用的 skill |
| --- | --- | --- |
| 已有具体工单 | 核对依赖 → 领取 → 实现 → 验证 → PR | `implement` |
| 明确的小改动 | 直接实现并做对应验证；涉及多人协作时建立一个 issue | `implement` |
| 报错、回归、性能异常 | 复现 → 缩小范围 → 验证假设 → 修复 → 回归验证 | `diagnosing-bugs` 或 `diagnose` |
| 需要跨会话或多人实施的需求 | 查代码和现有决定 → 澄清影响结果的缺口 → 持久化规格 → 拆工单及依赖 → 推进可开工任务 | `grill-with-docs` → `to-spec` → `to-tickets` |
| 界面取舍需要看到效果 | 先出无敏感数据的原型，确认视觉决定，写进规格后实施 | `prototype`；按环境选用 `impeccable` / `finesse-ui` |
| 交付前 | 对照规格与仓库约束审查差异，修复问题，报告验证证据 | `code-review`；写 PR 时用 `pr` |

小改动不必扩展成完整规划流程。已有规格和任务时直接复用，不重复拆分。只在缺失的产品决定会改变实现时询问用户；代码位置、配置和 GitHub 状态由 Agent 自己查。

## Skill 与 session

- 先检查当前平台实际提供的 skill，读取其说明再使用。用户目录中的 skill 不随仓库克隆，不能作为开工依赖。
- skill 标注 `disable-model-invocation: true` 时，不能承诺它会根据普通对话自动触发。没有该 skill 或不允许自动调用时，直接执行本文对应流程，并如实说明采用了仓库流程。
- 自动选择流程不要求先新建 session。当前上下文足够且下一阶段需要本轮讨论时继续；独立、范围明确的工作可使用平台提供的子 Agent / 独立上下文。
- 多 Agent 执行时，每个任务使用独立分支和工作区，并先完成 `collaboration.md` 的领取流程。只调度用户已授权的范围，按依赖推进；共享文件存在冲突时串行处理。
- 切换平台、设备或上下文前，先提交并推送可恢复的工作，在 issue 留交接记录。新 session 从 GitHub 恢复，不依赖 `/clear` 后的记忆。
- 能启动子 Agent 不等于能启动另一厂商或另一设备的服务。没有调度接口时，留下可直接领取的工单和交接；不要声称已启动外部 Agent，也不要假定 GitHub 会唤醒它。

## 工单发布门槛

一个没有本轮聊天记录、也没有本机私有文件的 Agent，必须能从 GitHub 确定以下每一项，才标记 `ready-for-agent`：

- 目的、范围和明确的验收条件；必要的取舍已记录，未决事项已指出。
- 仓库内规格 / 设计依据的链接；图形、颜色、尺寸或状态决定不能只存在于本地原型。
- 代码入口或查找线索，以及关联的存储、消息、兼容性约束。路径是定位提示，接手时仍须核实。
- 验证步骤、需要的假数据和能做 / 不能做的检查；真实简历、账号和 API Key 不作为测试依赖。
- 原生阻塞关系、父任务，以及可以从哪个分支开始。

讨论中改变验收标准时，先更新规格和受影响工单，再实现。把长期通用约束放在 `AGENTS.md` 或其指向的文档，功能决定放在规格，进度放在 issue / PR。

## 完成

提交并推送分支，附测试和界面证据，按 `collaboration.md` 更新 issue / PR。未执行的浏览器检查明确列出，不能把逻辑测试通过写成整体验收通过。一次交付后，只有发现反复出现的流程缺口才更新此约定，不给每个小改动增加流程步骤。
